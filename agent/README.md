# Агент генерации идей

Агентная часть курсовой работы Крыжного К.С. Сервис принимает задание от
транспорта, получает русский JSON от локальной instruct-модели Ollama,
проверяет результат и отправляет его транспорту по контракту РПЗ.
Frontend, Kafka и SSE находятся на других уровнях проекта.

## Выбор модели и способа запуска

По умолчанию используется `qwen3:4b-instruct-2507-q4_K_M`: 4 млрд параметров,
квантизация Q4_K_M, файл весов около 2,5 ГБ. Выбран отдельный Instruct-тег без режима размышлений. Это локальная модель с поддержкой
русского языка и структурированного вывода. На M5 Air с 16 ГБ предусмотрены
контекст 4096 токенов и одна одновременная генерация, чтобы ограничить память.
Размер весов не равен полной потребности в RAM: нужны также контекст, runtime,
macOS и Docker. Для ноутбуков с меньшей памятью можно выбрать
`qwen2.5:1.5b-instruct-q4_K_M`; качество следует проверить отдельно.

| Среда | Агент | Ollama | Ускорение |
| --- | --- | --- | --- |
| Mac Apple Silicon, рекомендуется | Docker | Нативно на Mac | Metal |
| Windows, рекомендуется при наличии GPU | Docker | Нативно на Windows | Поддерживаемый Ollama GPU |
| Windows/Linux без GPU | Docker | Docker | CPU |
| Windows WSL2/Linux с NVIDIA | Docker | Docker | NVIDIA, отдельный Compose |
| Разработка | Python 3.10+ | Нативно | Зависит от компьютера |

Ollama в Docker Desktop на macOS не получает Apple GPU, поэтому для Mac модель
работает вне контейнера. Это по-прежнему один агентный узел, соответствующий РПЗ.
Требуются Docker Desktop с Compose v2 и нативная Ollama; актуальная Ollama для
Mac требует macOS 14+. Python на хосте для Docker-варианта не нужен.

Источники: [модель](https://ollama.com/library/qwen3:4b-instruct-2507-q4_K_M),
[ограничения GPU Docker](https://docs.ollama.com/faq#how-do-i-use-ollama-with-gpu-acceleration-in-docker),
[macOS](https://docs.ollama.com/macos), [Docker Ollama](https://docs.ollama.com/docker).

## Mac M5 с 16 ГБ

Установить и запустить [Ollama](https://ollama.com/download/mac) и Docker Desktop.
Команды ниже выполняются в Terminal, начиная из корня репозитория:

```sh
ollama pull qwen3:4b-instruct-2507-q4_K_M
ollama run qwen3:4b-instruct-2507-q4_K_M ""
cd agent
cp .env.example .env
```

Прогрев модели не обязателен для запуска, но убирает время первоначальной загрузки
из первого пользовательского запроса. В `.env` указать адрес **компьютера транспорта**:

```dotenv
TRANSPORT_BASE_URL=http://192.168.1.20:8080
OLLAMA_BASE_URL=http://host.docker.internal:11434
```

Вместо примера IP можно использовать адрес ZeroTier. Затем:

```sh
docker compose up -d --build
docker compose logs -f agent
```

Проверить `http://localhost:8000/api/v1/health` и `http://localhost:8000/docs`.
HTTP 200 health означает, что Ollama доступна и выбранная модель установлена.
Модель ещё может быть не загружена в RAM — это не тест качества генерации.
`ollama ps` после генерации показывает использование GPU и размер памяти.

У исполнителя транспорта в его `transport/.env` должно быть:

```dotenv
AGENT_BASE_URL=http://192.168.1.30:8000
```

Здесь `.30` — Mac агента, `.20` — компьютер транспорта. Открыть входящий TCP 8000
на Mac и 8080 на транспорте. В распределённой системе `localhost` обозначает
текущий компьютер, а внутри Docker — текущий контейнер.

Остановить контейнер: `docker compose down`. Завершить нативную Ollama отдельно,
если модель больше не нужна. Интернет нужен для первоначального скачивания образов,
Python-пакетов и весов; генерация выполняется локально без ключей внешних LLM API.

## Windows PowerShell

Установить Docker Desktop с WSL2 и [Ollama](https://ollama.com/download/windows),
запустить обе программы. В PowerShell из корня репозитория:

```powershell
ollama pull qwen3:4b-instruct-2507-q4_K_M
ollama run qwen3:4b-instruct-2507-q4_K_M ""
Set-Location agent
Copy-Item .env.example .env
```

Указать `TRANSPORT_BASE_URL` в `.env`, затем:

```powershell
docker compose up -d --build
Invoke-RestMethod http://localhost:8000/api/v1/health
```

Если Docker не может обратиться к нативной Ollama через `host.docker.internal`,
проверить доступ к 11434 с контейнера и настройки привязки Ollama. При необходимости
задать `OLLAMA_HOST=0.0.0.0:11434` для процесса Ollama и перезапустить его.
На Mac приложение читает переменные через `launchctl setenv OLLAMA_HOST "0.0.0.0:11434"`,
на Windows — через переменные окружения пользователя. Ограничить доступ к порту
локальным компьютером/доверенной сетью. Это не переменная агента в `.env`.
См. [настройку сервера Ollama](https://docs.ollama.com/faq#how-do-i-configure-ollama-server).

## Полностью в Docker

На CPU, из `agent/`, после копирования `.env.example` в `.env`:

```sh
docker compose -f compose.yaml -f compose.ollama.yaml up -d --build
```

Сначала запускается Ollama, затем `model-init` скачивает выбранную модель в volume,
и только после успешного скачивания запускается агент. Код завершения 0 и состояние
Exited у `model-init` штатны. Порт модели наружу не публикуется. Обновление модели
в `.env` требует повторного `up` с теми же Compose-файлами.

Для NVIDIA на Windows с WSL2 или Linux при настроенном NVIDIA Container Toolkit:

```sh
docker compose -f compose.yaml -f compose.ollama.yaml -f compose.nvidia.yaml up -d --build
```

Останавливать нужно с тем же набором `-f`. Без `-v` скачанные модели сохраняются.
На Mac полная контейнеризация работает на CPU; для демонстрации предпочтительна
нативная Ollama. Если CPU не укладывается в дедлайн, выбрать 1.5B или согласованно
увеличить тайм-ауты агента и транспорта. `OLLAMA_IMAGE` позволяет закрепить версию
образа или digest вместо `ollama/ollama:latest`.

## Запуск без Docker

Из корня репозитория, macOS/Linux:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r agent/requirements.lock
cd agent
cp .env.example .env
```

В `.env` заменить `OLLAMA_BASE_URL` на `http://127.0.0.1:11434` и указать адрес
транспорта. Если транспорт на этом же компьютере — `http://127.0.0.1:8080`.

```sh
../.venv/bin/python -m app
```

Для PowerShell создать окружение через `py -3.12 -m venv .venv`, устанавливать
пакеты через `.venv\Scripts\python.exe`, а из `agent/` запускать
`..\.venv\Scripts\python.exe -m app`. Активировать окружение необязательно.
Python 3.12 используется в Docker и проверках; исходный код совместим с Python 3.10+.
Установленные в системе Python 3.9 и более ранние версии не подходят.

## Контракт

Swagger UI: `/docs`, спецификация OpenAPI 3.0.3: `/openapi.json` и
[`agent.openapi.yaml`](agent.openapi.yaml).

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/v1/generate` | 202 и адрес диагностики |
| GET | `/api/v1/generations/{messageId}` | Состояние задания либо 404 |
| GET | `/api/v1/health` | 200 при доступной Ollama и установленной модели, иначе 503 |

Пример тела POST:

```json
{
  "messageId": "8d964744-5b5c-4c3b-91f1-6f54e325c979",
  "sender": "Кирилл",
  "sentAt": "2026-11-22T17:00:00+03:00",
  "topic": "Как первокурснику освоиться в университете",
  "contentType": "video",
  "requirements": "Для студентов, доступно и с практическими примерами",
  "ideaCount": 12
}
```

Проверять полную систему нужно через **POST транспорта `/api/v1/requests`**:
транспорт сначала регистрирует UUID, а затем вызывает агента. Прямой POST агенту
без предварительной регистрации UUID у транспорта закончится ошибкой доставки 404.
Для самостоятельной проверки модели предусмотрен скрипт ниже.

`messageId` — UUID v4; `sentAt` — RFC3339 с часовым поясом, его текст сохраняется.
Имя обрезается по краям и ограничено 50 символами, тема — 500, пожелания — 2000.
Форматы: `blog`, `video`, `post`, `post_series`, `other`.
`ideaCount` — строго целое 10–15, по умолчанию 12, пожелания по умолчанию пустые.
Неизвестные поля и `null` вместо необязательных значений отклоняются.
Тело ограничено 64 КиБ, включая запросы с потоковым телом.

Повтор нормализованного запроса с тем же UUID возвращает прежнее 202 и не запускает
модель повторно. Другие параметры с занятым UUID дают 409. Состояния:
`accepted → generating → sending → completed`, при ошибке — `failed`.
`completed` обозначает подтверждённую HTTP-отправку всех сегментов; пользовательский
успех определяется только транспортным `generation_completed` после сборки.

Результат содержит исходные UUID, время, тему, формат, количество, отправителя
`content-ideas-agent` и `groups`. Модель генерирует содержимое групп и внутреннее поле `theme`, чтобы заранее
разделить аспекты темы. Пустые и повторяющиеся темы групп отклоняются. `theme`
не передаётся транспорту; служебные метаданные агент добавляет сам. Проверяются длины, обязательные поля,
сквозная нумерация, разные заголовки и точный план групп:

| Идеи | Размеры групп |
| --- | --- |
| 10 | 3 + 3 + 4 |
| 11 | 3 + 4 + 4 |
| 12 | 4 + 4 + 4 |
| 13 | 3 + 3 + 3 + 4 |
| 14 | 3 + 3 + 4 + 4 |
| 15 | 3 + 4 + 4 + 4 |

После валидации агент сериализует JSON один раз, вычисляет SHA-256 точных байтов,
регистрирует манифест и последовательно отправляет сегменты до 512 байт UTF-8.
Пауза между сегментами по умолчанию 150 мс. HTTP 202 не повторяется: транспорт
мог специально отбросить этот сегмент. Повтор одинакового HTTP-тела допускается
только при сетевой ошибке/5xx, ограниченно; 4xx завершают отправку.

Ошибки после 202 передаются в `/api/v1/messages/{messageId}/failure`:
`MODEL_UNAVAILABLE`, `GENERATION_TIMEOUT`, `GENERATION_FAILED`, `DELIVERY_FAILED`.
Невалидный ответ модели не превращается в успешный результат и не отправляется
частично. Если уведомление не дошло, диагностика содержит `failureNotified=false`,
а транспорт завершает запрос собственным таймером.

## Настройки

Все параметры и значения по умолчанию перечислены в [`.env.example`](.env.example).
Основные ограничения:

- `GENERATION_TIMEOUT_SECONDS=110` включает очередь и все попытки генерации;
  он должен быть меньше дедлайна транспорта до манифеста, по РПЗ — 120 секунд.
- `MODEL_ATTEMPTS=2`: одна генерация и один корректирующий запрос в рамках общего дедлайна.
- `MAX_CONCURRENT_GENERATIONS=1`, `MAX_PENDING_JOBS=4`: ограничение памяти и очереди.
  Переполнение даёт 503; ожидание в очереди не продлевает дедлайн.
- `SEGMENT_DELAY_MS=150`, допустимо 100–300; размер сегмента фиксирован 512 байт.
- `DELIVERY_TIMEOUT_SECONDS=3`, `DELIVERY_ATTEMPTS=2`: ограниченные сетевые повторы.
- `TERMINAL_TTL_SECONDS=900`: хранение диагностики завершённых задач 15 минут.

Запускать **один Uvicorn worker и один экземпляр агента**. Задания и дедупликация
хранятся в памяти. После перезапуска нужны новые UUID; постоянной истории нет.
Приложение не принимает callback URL и не даёт модели инструментов сетевого доступа.
Адрес транспорта задаёт только администратор через окружение.

## Проверки

Из корня репозитория установить `agent/requirements-dev.txt`, затем из `agent/`:

```sh
../.venv/bin/python -m pytest -q
../.venv/bin/ruff check .
../.venv/bin/ruff format --check .
```

Тесты не требуют работающей Ollama, Docker или Kafka. Если рядом есть `transport/`,
интеграционные проверки автоматически используют его настоящий код с подставной
очередью. Можно указать другой checkout транспорта:

```sh
TRANSPORT_SOURCE_DIR=/path/to/transport ../.venv/bin/python -m pytest -q
```

Для настоящей Ollama, с предварительно скачанной моделью:

```sh
../.venv/bin/python scripts/smoke_local.py --count 12
../.venv/bin/python scripts/smoke_local.py --count 15 --content-type post --output reports/post-15.json
```

Скрипт вызывает реальную модель через HTTP API агента, принимает сегменты
проверяющим локальным приёмником вместо транспорта и сверяет схему, UTF-8, длину,
нумерацию и SHA-256. Подробный отчёт, включая идеи и длительность, сохраняется в
`reports/`; код возврата 0 означает успех. Это не сквозной тест Kafka/SSE.
Итоги выполненных проверок: [`docs/validation.md`](docs/validation.md).

После изменения схем пересобрать спецификацию:
`../.venv/bin/python scripts/export_openapi.py`.
Docker устанавливает проверенные версии из `requirements.lock`; `requirements.txt`
задаёт допустимые диапазоны для последующего обновления.

## Интеграция и диагностика

При штатной учебной потере 10% транспорт часто не собирает полный ответ из многих
сегментов. Это предусмотренный сценарий РПЗ. Для демонстрации успешного пути
временно задать у **транспорта** `LOSS_PERCENT=0`, затем вернуть 10 для проверки ошибки.
Агент не пересылает пакеты с подтверждением 202 и не скрывает потери.

Health 503 с `ollama=down`: проверить адрес и процесс Ollama. `modelReady=false`
при `ollama=up`: выполнить `ollama pull` для точного тега из `.env`.
`GENERATION_TIMEOUT`: проверить GPU через `ollama ps`, прогреть модель, сократить
другую нагрузку или выбрать меньшую модель. `DELIVERY_FAILED`: проверить IP,
порт транспорта, регистрацию UUID и его журнал.

В текущем контракте транспорта у группы только `groupNumber` и `ideas`;
заголовка группы нет. Модель создаёт внутренние названия тематических групп, но добавить
отдельное поле заголовка без согласования схем трёх уровней нельзя.
Другие расхождения документа и кода перечислены в [`docs/requirements.md`](docs/requirements.md).
